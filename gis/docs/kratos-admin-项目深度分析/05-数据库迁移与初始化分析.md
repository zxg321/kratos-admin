## TL;DR

- 运行时主库实为 PostgreSQL（:5455），而根 README 与 docs 仍以 MySQL 为主线描述存在文档滞后，迁移资源同时内置 mysql/ 与 postgres/ 两套方言目录（详见 §1 数据源核实）。
- 迁移采用"**唯一版本 v0.0.1 全量初始化**"策略：不新增 v0.0.2 或增量迁移，所有新功能直接补齐 v0.0.1，SQL 幂等（`INSERT IGNORE` 等），已执行过的库不会重放。
- 启动顺序：GORM AutoMigrate 建表 → 按序执行 v0.0.1 `.up.sql` → 同步多语言译文到 `base_i18n` → 重建 OpenAPI 接口元数据（`base_api`）→ 同步租户菜单 → 重建 Casbin 策略。
- 迁移文件通过 `backend/migration/migration.go` 的 `//go:embed assets/*` **内置于后端二进制**，经 `internal/module/resources.go` 以 `module.Migrations{Name:"admin", FS, Path:"."}` 注册给 kratos-core 执行；数据库只存迁移引用与执行记录（`base_migration` 表），未发现独立 checksum 校验机制；历史文件需永久保留。
- CI 有专门的 `pg-migration-sql.yml` 工作流，用 pglast（libpg_query 绑定）做无数据库的 PG 语法校验。

## 2. 配置体系

`backend/configs/` 共 23 个 yaml，分层机制为：基础配置 `<name>.yaml` + 环境覆盖 `<name>.<env>.yaml`（存在则叠加，不存在回退基础配置）。

| 配置文件 | 用途 |
| --- | --- |

| `key.yaml` / `key.dev.yaml` / `key.docker.yaml` | Vault 根密钥（密钥派生、配置解密），不回退本地文件 |

| `mfa.yaml` / `mfa.dev.yaml` | TOTP/WebAuthn，`mfa.encryption_key` 留空时按 `kratos-kit:mfa/encryption` 派生 |

## 3. 迁移机制

### 3.1 目录规则

```text
backend/migration/assets/v0.0.1/<database-type>/<feature>.up.sql
backend/migration/assets/v0.0.1/<database-type>/README.md            # → base_migration.description
backend/migration/assets/v0.0.1/<database-type>/README.<locale>.md   # → base_i18n 译文
backend/migration/assets/v0.0.1/<database-type>/<data-source>/...    # 命名数据源
```

- 当前两方言目录：`mysql/`（7 个脚本 + 4 语言 README，属遗留/兼容资产）、`postgres/`（6 个脚本；CI 校验 PG 语法；**无 language.up.sql，语言记录并入 default_data.up.sql**）。
- 脚本按文件名排序执行；唯一版本 v0.0.1，新功能直接改写该版本，不新增增量迁移。
- 迁移记录唯一键 = 模块 + 数据源 + 版本；一个版本内任一脚本失败 → 回滚该版本并阻止服务启动，修复后重启重试。

### 3.2 初始化内容（default_data.up.sql + i18n.*.up.sql + base_area/base_redact_rule/language）

- 默认租户、部门、岗位、角色；开发账号 `super / 112233`、`admin / 112233`（部署前必须改密）。
- 系统配置、字典、菜单、按钮、服务方法权限（含 AI、代码生成、开放授权、MFA 入口）。
- 地区基础数据（`base_area`）、脱敏规则（`base_redact_rule`）、语言记录（`base_language`）。
- 多语言译文经 `base_i18n.target_type` 写入（菜单/字典/配置名/任务名）。

部分表（MFA 四表、`oauth_client`、翻译表、代码生成 `i18n_config`）由 GORM AutoMigrate 创建，不走 SQL 脚本。

### 3.3 GIS 侧

`gis/backend/migration/assets/v0.0.1`：图层、要素、图层授权三类空间表（M1），空间数据使用 PostgreSQL + PostGIS（SRID 4326，独立 `gis` 库，表前缀 `gis`）（现状库名 gis，目标态按 D6 为 snop_gis）。

## 5. 亮点与技术债

**亮点**
1. 唯一版本 + 幂等 SQL + 启动时自动重建 API/Casbin 元数据，环境重建成本低、漂移面小。
2. 迁移描述即文档（README.md → base_migration.description），且纳入 i18n 体系。
3. CI 对 PG 迁移做纯静态语法门禁，不需要真实数据库即可拦截语法错误。
4. 双方言资源结构清晰，为多数据库留了扩展位（D6 锁定 PostgreSQL 后，mysql/ 方言是否保留待定，本建议暂缓执行）。

**技术债 / 风险（P0-P2）**
- **P0｜文档与实际数据库不一致**：根 README 与 docs/数据库与初始化数据设计.md 仍写 MySQL 主线，实际配置为 PostgreSQL。新成员按文档建 MySQL 库会直接启动失败。
- **P1｜v0.0.1 永不重放**：已记录 v0.0.1 的存量库不会自动获得脚本修改后的新初始化数据，必须靠 AutoMigrate 或人工补数；文档已提示但缺系统化的"存量库升级 checklist"。
- **P1｜`data.yaml` 中 `debug: true`、明文密码 `postgre/postgre` 入库**：基础配置（会进 Git）不应包含调试与真实凭据，应下沉到 `data.dev.yaml` 或 `ENC[...]`。
- **P2｜mysql/ 与 postgres/ 脚本内容一致性无自动对比**：新增功能若只改一方言目录，另一方言静默漂移；建议 CI 增加"两目录文件清单一致性"检查（pg-migration-sql.yml 只校验 PG）（同上，暂缓执行）。
