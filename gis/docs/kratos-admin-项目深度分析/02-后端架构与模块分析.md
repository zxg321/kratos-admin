## TL;DR

- 单 Go module（`github.com/liujitcn/kratos-admin/backend`，Go 1.27.0），Kratos v3 + 自研 kratos-core（v0.0.31 宿主框架）+ kratos-kit（v0.0.85 全家桶：auth/authz/casbin、database/gorm、queue、sse、mcp、oss、redact 等）+ GORM v1.31。
- 分层纪律严格：**Proto 是唯一契约源**，`api/proto → api/gen/go → service（薄）→ biz（业务）→ data/gen（GORM 生成，禁止手写 SQL）`，全链路生成物不可手改。
- 可插拔设计成熟：`bootstrap.go` 输出 Resources/Modules/Tasks/Streams/Consumers 五类具名贡献，外部项目可把 admin 作为模块挂进 kratos-core 宿主；`adapter/core`、`adapter/kit` 是与 internal 平级的公开适配器。
- 双数据库支持（mysql + postgres 驱动均已注册、迁移双方言、备份双 dump），**当前部署以 PostgreSQL :5455 为主**。
- 主要风险：service/data 层测试覆盖极薄、internal/adapter 参数列表人工同步、配置体系复杂度高。

## 2. 目录职责与请求链路

```text
api/proto/{base/v1, system/admin/v1, system/app/v1, system/common/v1, system/config/v1}
  → api/gen/go                     # Buf 7 插件：Go/gRPC/Kratos HTTP/errors/agent-tool/mcp-tool/redact
  → internal/service/...           # 薄传输适配 + 错误兜底
  → internal/biz/{base, system/admin, system/app, agent, backup}
  → internal/data/gen              # gorm-kit 生成 models/query/仓库（53 张表清单驱动）
```

典型 user 链路：`api/proto/system/admin/v1/base_user.proto` → `internal/service/system/admin/v1/base_user.go` → `internal/biz/base/base_user.go`（BaseCase）→ `internal/data/gen/query/base_user.gen.go`。

跨模块数据访问只能走生成客户端，不公开内部 Model/Query/Repository/Case（`backend/README.md` 明确纪律）。

## 4. 可插拔机制（核心亮点）

- `module.Module`（kratos-core/module）：`internal/module/module.go` 实现 RegisterGRPC/RegisterHTTP/RegisterMCP，聚合 base/admin/app 三组 Services。
- `bootstrap.go` 对外输出 `AdminResources / AdminModules / AdminTasks / AdminStreams / AdminConsumers` 五个具名类型；外部宿主合并 `backend.ProviderSet` + `kratoscore.ProviderSet` 即可托管 admin。
- Resources（`internal/module/resources.go`）：Models / I18n / OpenAPI / Migrations 四类资源，模型来自 `internal/data/gen/data.Models()`。
- SSE 流（`internal/biz/system/admin/sse/init.go`）：Codegen / Notification / OpsMonitoring / RuntimeConsole 四类。
- 队列消费者：`base.message.dispatch` + 审计事件 `admin.log.event`。
- 定时任务（`internal/task/init.go`）：5 个任务（I18n、消息投递、归档、日志回退、备份），Redis 分布式锁，锁初始化失败降级内存锁（仅单实例）。

## 5. 中间件与横切能力

| 能力 | 实现位置 | 要点 |
| --- | --- | --- |
| 认证/授权 | kratos-kit authn/authz（Core 挂载） | JWT access/refresh；Admin 追加 LogMiddleware、sessionpolicy、passwordpolicy、RuntimeAccessMiddleware（`internal/module/module.go`） |
| OAuth Filter | `internal/server/middleware/oauth/*` | 单表 JSON operation 白名单；HTTP 加解密 Filter 绑定前后 |
| 审计异步 | `internal/server/middleware/log/log.go` | 请求线程→内存 buffer(2048)→`admin.log.event` Redis 队列→Consumer 落库；失败写 HMAC 签名 jsonl 兜底 |
| i18n | `internal/i18n/assets/*.json`（4 语言内嵌） | 交 Core 统一注册，配合 protovalidate 规则 ID |
| 配置 | 24 个 yaml（base/dev/docker/https/local 多层） | `<name>.yaml` + `<name>.<env>.yaml` 覆盖；Vault 不可用启动失败不回退 |
| 日志兜底 | runtimeconfig 表单配置 `baseLogFallback` | 每日任务回灌日志表 |

## 6. 构建与生成链

- `make api/openapi`：buf generate → `api/gen/go` + OpenAPI；含 import 别名规范化（normalize-go-imports）与 I18N→I18n 批量改名，保证生成幂等。
- `make gorm-gen`：按 `GORM_TABLE`（53 张表）从开发库生成，生成后用 perl 正则修正生成物（依赖生成器行为不变，脆弱点）。
- `make public-wire` / `make wire`：双 Wire 图（模块装配 + 独立启动入口）。
- 多端 TypeScript RPC：`api/buf.{admin,uni-app,taro-app}[.core].typescript.gen.yaml` 用 ts-proto 直出三端 `src/rpc` 目录。

## 7. 测试现状

约 50 个 `*_test.go`，集中在高风险点：脱敏（adapter/kit）、OAuth 加解密、备份加解密、codegen 回归（generation_regression_test.go）、wiring 一致性（codegen_wiring_test.go）。**`internal/service/system/admin/v1`（60+ 文件）与 `internal/data` 几乎无测试**（仅 file_http_test.go 一例），业务 CRUD 无集成测试。

## 8. 亮点与技术债

**亮点**
1. 宿主/插件边界清晰：外部生成代码不引用 backend/internal，adapter 只暴露 Core 公共类型。
2. 生成链完备幂等，"生成物不可手改"纪律贯彻到 lint（禁止手写 SQL 检查，`backend/Makefile`）。
3. 审计两级异步（内存 buffer + Redis 队列）+ 文件兜底，兼顾吞吐与不丢。
4. 备份模块端到端完整性设计（加密+校验+回读）。

**技术债 / 风险（P0-P2）**
- **P1｜service/data 层测试覆盖极薄**：60+ service 文件无测试，核心 CRUD 全靠生成器正确性兜底；建议优先补 biz 层用例与一条端到端集成链路。
- **P1｜internal/module/wire.go 的 BuildModules 与 bootstrap.go NewModules 参数列表（13 个参数）人工同步**：有 codegen_wiring_test.go 兜底但仍脆弱，改签名需两处同改。
- **P2｜gorm-gen 依赖 perl 正则后处理**：生成器升级即可能破坏。
- **P2｜Go 1.27.0 属较激进版本**：需确认团队与 CI 工具链一致性（CI 用 go-version-file 对齐，尚可）。
- **P2｜Windows 路径处理散落在 Makefile**（GO_BIN_DIR 反斜杠替换）：跨平台维护成本。
