## 📌 TL;DR

- GIS1.0（Jeecg 单体）+ GIS2.0（Spring Cloud 微服务）合计约 **210+ Controller、150~160 张表、4 套前端**，功能覆盖管网一张图、五类空间分析、IoT 监测（7+ 厂商）、巡检闭环、工单、EAM、DMA 漏损、指挥调度、大屏、两级租户后台。
- 重构方向已收敛：**用 kratos-admin 技术栈（Go + Kratos v3 + PostgreSQL/PostGIS + Vue3 monorepo + AMap）统一承接**，GIS2.0 内置的两版 openspec 迁移提案与本仓 20260913 落地方案互相印证，落地路径成熟。**2026-09-14 决策更新**：地图保留 AMap、暂不引 CesiumJS、RBAC 全新自建（不复用 admin 系统）、字典按子系统独立——详见 ADR-12。
- 2026 趋势增量机会（在基础重构之上叠加）：**PostGIS 空间函数下沉分析算法、时空时序一体化（TimescaleDB/TDengine）、Geo-Agent（MCP 已在仓内具备工具生成链）、二三维一体化（3D Tiles/CesiumJS）、云原生部署（K8s/对象存储瓦片）、低空无人机巡检、端侧/云端 GeoAI 双流水线**。
- 关键决策点：一次到位统一底座（推荐，pg18-unified 提案）vs 绞杀者分批迁移；DMA/EAM/cnd 三个缺口域需明确承接。

## 2. 技术栈映射与重构原则（继承既有结论 + 强化；地图与 RBAC 决策已按 ADR-12 更新）

> **平台定位（ADR-12 D7）**：重构目标为**智慧能源运营管理一体化平台，代号 SNOP**；GIS 为其子模块（与巡检/IoT/指挥调度/资产/auth 等并列），介质分型按租户级配置扩展至能源运营全域（燃气/水务/热力等）。

| 维度 | 决策 |
|---|---|
| 数据库 | **一律 PostgreSQL；每个子系统独立一个库（ADR-12 D6/D7）**：`snop_system`(auth/acl+平台配置) / `snop_gis`(GIS 核心+DMA，PostGIS 4326) / `snop_patrol`(巡检，PostGIS) / `snop_iot`(IoT，TimescaleDB 或外接 TDengine) / `snop_cnd`(指挥调度) / `snop_asset`(EAM)。经 `data.databases` 命名数据源 + 迁移目录 `<database-type>/<data-source>/` 落地；**禁止跨库 JOIN**，跨域只存 ID+契约取数；空间数据从 JSON 文本坐标迁为 geometry 列 + GiST 索引 |
| 时序 | IoT 独立库 `snop_iot` 内用 **TimescaleDB**（统一 PG 运维面）或外接 TDengine（REST 驱动）；巡检轨迹时序数据存 `snop_iot` 或 `snop_patrol`（按访问路径定）；禁新增 MySQL |
| 后端 | Go + Kratos v3 模块化（auth/acl + gis/patrol/iot/cnd/dma/asset 各域独立 proto + module） |
| 认证/RBAC | **一套登录贯通四端（同一 JWT 签发域）**；但**用户/角色/菜单/权限全新自建**（独立 auth/acl 域，按 GIS 业务角色矩阵重新设计），**不复用 kratos-admin admin 系统**——实现可借鉴 kratos-kit authn 中间件，数据模型不继承 base_*（ADR-12 D4） |
| 数据字典 | **各子系统独立字典表**（gis_dict/patrol_dict/iot_dict…，同构模板生成、数据独立、按子系统切换的管理界面），不做集中收敛（ADR-12 D5） |
| 前端 | Vue3 monorepo（pnpm+turbo）：GIS 工作台 / 管理后台 / 大屏分应用组织；移动端 uni-app；不引入 micro-app |
| 引擎 | **保留高德 AMap JSAPI（同 GIS1.0/2.0），不迁移 MapLibre**；GISMap 包（绘制/量算/吸附/打点插件）直接演进复用；库内 WGS84、展示 GCJ02（gcoord 入库即转换）；key 走配置不入库（ADR-12 D2） |
| 3D | **暂不引入 CesiumJS**；数据模型预留 z 值/高程字段，确有 3D 孪生订单再评估 CesiumJS 或 AMap Loca 3D（ADR-12 D3） |
| 契约 | proto 驱动 + make gen 全链生成（仓内纪律），BPM/厂商设备以适配器承接 |

## 3. 2026 趋势对标：目标系统的升级机会

以下按"对本项目价值 × 落地成本"排序，标注与仓内现状的关系。

### 3.1 空间分析下沉 PostGIS（趋势：云原生空间数据库成熟，PostGIS 3.6 支持 GeoParquet/Arrow）
- **现状**：GIS2.0 五类分析全在 Java 应用层 O(N)，本仓草案仍计划"纯内存图"。
- **建议**：关阀/连通性采用 **内存图 + PostGIS bbox 预筛混合**（旧文档 P0 已定）；进一步把缓冲/叠加/测积全部走 PostGIS 函数（已实现）；图数据以 `gis_pipe/pipe_point` 物化，必要时用 **Apache AGE**（pg18-unified 提案已含）做图查询，避免自研遍历的性能天花板。
- 价值 9/成本 3 → **P0**。

### 3.2 时空一体化：时序 GIS 成标配（趋势 7）
- IoT 百万级轨迹回放、动态仿真。**建议**：巡检轨迹/设备遥测统一接时序库；`staff_track` 轨迹回放直接用时序窗口查询 + AMap 动态渲染；预留动态协议接口位。
- 价值 8/成本 4 → **P1**。

### 3.3 Geo-Agent：MCP 工具链是本仓"隐藏王牌"（趋势 1/6：SuperMap AgentX、Mapbox MCP 预测、MCP+A2A 多智能体）
- **仓内现状**：Kratos 已具备 **proto → Agent Tool / MCP Tool 自动生成链**（buf 插件），base 已有 AI 会话底座。
- **建议**：把五类管网分析 + DMA 漏损 + 巡检统计注册为 MCP 工具，立即获得"自然语言管网分析 Copilot"能力——这正是 GIS2.0 内置 PipeMind AI Copilot PRD 想做的事，成本近乎为零。后续按 A2A 思路让"告警分析 Agent / 工单 Agent"协作。
- 价值 9/成本 2 → **P0（性价比最高的一项）**。

### 3.4 二三维一体化与数字孪生（趋势 4/6：BIM+GIS+CIM、3DGS、CesiumJS MVT 原生支持）
- GIS1.0 已有 scene.babylon 尝试、push_zy_pipe_bim 表；GIS2.0 有 BIM 推送域。
- **建议（按 ADR-12 D3 调整）**：当前**不引入 CesiumJS**。若出现大屏 3D 需求，先用 **AMap Loca / AMap 3D 的管线挤出与热力渲染**（与既有引擎同栈，零新增引擎）；**确有 3D 数字孪生订单**时再评估 CesiumJS（届时 MVT→3D Tiles 已打通）。3DGS/glTF 2.1 只做技术跟踪；数据模型预留 z 值/高程字段。
- 价值 7/成本 6 → **P2（订单触发）**。

### 3.5 低空经济 × 无人机巡检（趋势 8）
- 巡检域天然可扩展无人机航线取证、禁飞区分析。**建议**：patrol 域的 online_upload/video_evidence 预留无人机媒体接入与航线规划接口位，不提前建域。
- 价值 6/成本 5 → **P2 预留**。

### 3.6 云原生部署与信创（趋势 3/7、信创合规）
- **现状**：compose 仅容器化应用，中间件靠宿主机。**建议**：补 K8s manifests/Helm（PostGIS/Redis/Consul/Vault 有官方 chart）；瓦片服务走对象存储（MinIO 已接）；多架构镜像链已具备（amd64/arm64）→ 天然适配飞腾/鲲鹏信创环境；权限/审计设计可对照 kratos-admin 已过基线的审计/脱敏实践（自建时沿用同等标准）。
- 价值 7/成本 4 → **P1**。

### 3.7 端侧 GeoAI 与生成式能力（趋势 5）
- 遥感分割端侧化、文本生成样式。与本项目关联弱（无遥感业务），仅在 AI 会话底座上保留"文本→地图样式/查询"的 LLM 接口位。价值 4/成本 5 → **观察项**。

## 5. 风险与对策（10 分制评分见文末）

1. **范围爆炸**（最大风险）：7+ 域 150 表。→ 严格按域分期，每域"映射清单+契约"验收后再开下一域；GIS2.0 的表映射清单文档可直接作为输入。
2. **坐标漂移**：1.0/2.0 库内 CGCS2000+GCJ02 混存。→ 入库即转 WGS84，前端才转 GCJ02；写转换流水线 + 抽样比对验收。
3. **数据迁移质量**：JSON 文本坐标→geometry 列需全量解析校验。→ 写一次性 ETL（Python/GDAL），失败行进隔离表人工修复。
4. **IoT 厂商适配重写**：7+ 厂商私有协议。→ 消息 schema 先行、逐厂商灰度、BRT HTTP 轮询兜底保留。
5. **DMA 算法保真**：六步法是业务know-how。→ 先冻结 1.0 算法行为基线（黄金用例），重写后对拍验证。
6. **cnd 半成品**：只有表和原型。→ 当作新需求而非迁移，用 code_gen 起步。

## 7. 两个既有迁移提案的取舍

| 提案 | 思路 | 建议 |
|---|---|---|
| `go-kratos-vue3-refactor`（绞杀者） | 9 Java 服务分批替换，库表不动 | 适合"不能停机"的过渡；但保留 MySQL/旧 schema，长期还清一次债 |
