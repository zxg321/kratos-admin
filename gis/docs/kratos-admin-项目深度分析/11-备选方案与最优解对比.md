# 备选方案与最优解对比（重构路线决策）

> GIS1.0 / GIS2.0 重构升级分析 · 11
> 日期：2026-09-14
> 定位：09 文档给出"推荐主线"，本文把**所有可行方案（含更好的替代解）**摆到同一桌面对比，供决策

---

## 1. 四个整体方案

### 方案 A｜绞杀者分批迁移（GIS2.0 内置提案 go-kratos-vue3-refactor）
9 个 Java 服务逐个替换为 Kratos 服务（gis-public→iot→gis-core/patrol→admin/网关），**库表不动、双跑过渡**。
- ✅ 可随时停、风险分段、业务不中断
- ❌ 保留 MySQL/JSON 坐标/旧 schema，技术债只换运行时不换数据层；双体系并存期长；150 表映射做两遍（先迁运行时再迁数据）

### 方案 B｜统一底座一次性重建（GIS2.0 内置提案 go-kratos-v3-pg18-unified）
Kratos v3 + PostgreSQL 18 一体化（PostGIS+TimescaleDB+AGE+pgvector），库表 schema 重建，前端不重写。（按 ADR-12 D6 落地为：统一 PG 技术底座 + 每子系统独立一个库）
- ✅ 与 kratos-admin PG-only 纪律一致，一次清偿三大债（MySQL 多库/JSON 坐标/应用层分析）；运维面单一
- ❌ 需要一次"停旧开新"的数据割接窗口；初期一次性投入大

### 方案 C｜底座复用 + 事件驱动数据面 + Geo-Agent（本文推荐的改良最优解）⭐
在 B 的骨架上做三处关键升级（底座复用范围已按 ADR-12 收窄）：
1. **底座选择性复用**：文件/OSS、消息投递、任务调度、SSE、代码生成、MCP 生成链等**无账号耦合**的能力仍来自 kratos-admin 现成实现；但**认证后的 RBAC 体系（用户/角色/菜单/权限/字典/租户）全新自建**——不复用 admin 系统的 base_user/base_role/base_menu/base_dict（ADR-12 D4/D5）。
2. **数据面改事件驱动**：IoT 接入不做成同步 CRUD 服务，而是 **MQTT 接入网关 → 事件总线（Redis Stream 起步，NATS 可演进）→ 消费者（告警/入库/推送/分析）**。理由：8 厂商适配 + 告警链 + WebSocket 推送在 GIS2.0 里是三处独立 WebSocket + 同步调用，事件化后新增厂商/告警规则只需加消费者；gis2.0-redesign PRD 本身已规划事件总线，落进 Kratos 用仓内已有的 queue 运行时（Redis 队列消费者机制现成）。
3. **Geo-Agent 差异化先行**：五类分析 + DMA + 巡检统计先注册 MCP 工具（buf 生成链现成），让重构后的第一批交付物就是"自然语言管网分析 Copilot"——这既是 2026 主流方向（SuperMap AgentX / Mapbox MCP 预测），又把"算法重写正确性验证"变成人可对话检验的过程。
- ✅ 复用最大化 + 数据面为将来低空/视频/更多传感器预留扩展点 + AI 能力成为产品卖点
- ❌ 事件驱动对团队是新范式；需要好的死信/回放约定

### 方案 D｜SaaS 产品化重构（更远一步）
在 C 基础上把介质分型（燃气/水务/热力）升级为**租户级产品模板**：同一套 schema + 租户级功能开关（base_config/菜单分型已支持），把 DMA、巡检、IoT 做成可选模块，输出为多租户管网 SaaS。
- ✅ 三系统合并后天然多租户（maida 多企业 + kratos-admin 租户体系），一次重构沉淀为可复售产品
- ❌ 商业决策前置，超出纯技术重构范畴；建议作为 C 的演进方向而非起点
- **已决策**：D8 确认为商业演进路线（C 完成后启动），详见 `../snop-实施规划/03-SaaS产品化演进方案.md`。

### 对比矩阵

| 维度 | A 绞杀者 | B 统一底座 | **C 事件驱动+Agent ⭐** | D SaaS 化 |
|---|---|---|---|---|
| 技术债清偿 | 部分（运行时） | 完全 | 完全 | 完全 |
| 业务中断风险 | 最低 | 中（割接窗口） | 中（同 B，可灰度） | 中 |
| 一次性投入 | 中（周期长） | 大 | 大 | 更大 |
| 长期运维复杂度 | 高（双体系） | 低 | 低 | 低 |
| 扩展性（新传感器/新告警） | 差 | 中 | **好** | 好 |
| AI/2026 趋势收益 | 无 | 中 | **高** | 高 |
| 商业复用价值 | 低 | 中 | 中高 | **高** |
| 与 kratos-admin 纪律一致性 | 中 | 高 | 高 | 高 |

**推荐**：以 **C** 为主线（骨架=提案 pg18-unified，数据面=事件驱动，交付面=MCP 先行）；A 仅当存在"绝对不能停机的硬约束"时作为 fallback；**D 已确认为商业演进路线（已锁定，D8）**，C 完成后启动。

## 2. 六个关键技术分叉点

| 分叉点 | 选项对比 | 建议 |
|---|---|---|
| **库拆分策略** | 单库多 schema（集中）/ **每子系统独立一个库（ADR-12 D6：snop_system/snop_gis/snop_patrol/snop_iot/snop_cnd/snop_asset，平台代号 SNOP 见 D7）** / 每库独立实例 | **锁定独立分库**：同一 PG 实例起步，高负载域可平移独立实例；跨域只存 ID+契约取数，禁止跨库 JOIN；迁移目录按 `<database-type>/<data-source>/` 组织（kratos-admin 命名数据源机制现成） |
| **时序库** | TDengine（GIS2.0 现用，独立运维）/ TimescaleDB（PG 内置，统一运维）/ PG 分区表（最简） | **TimescaleDB（置于 snop_iot 独立库）起步**；设备量大（>1万点位）且已有 TDengine 运维经验时保留 TDengine。不建议引入第三种新时序库 |
| **图计算** | Apache AGE（PG 图扩展，SQL 图查询）/ 纯内存 Go 图（可单测，规模受限）/ 图数据库（Neo4j，新运维面） | **内存图 + PostGIS bbox 预筛起步**（配黄金用例对拍），管网规模跨过 10 万节点级再评估 AGE——避免为了 5 类分析引入图数据库 |
| **地图引擎** | AMap（GIS1.0/2.0 现用，插件成熟）/ ~~MapLibre~~（方案已剔除）/ CesiumJS（真 3D，仅订单触发评估） | **锁定 AMap（ADR-12 D2）**：GISMap 包直接演进，绘制/量算/吸附零重写；库内 WGS84、展示 GCJ02；**MapLibre 迁移方案全部剔除不作备选**；硬指标：18-20 缩放级及以下必须清晰；**暂不引入 CesiumJS**，确有 3D 孪生订单再评估（ADR-12 D3） |
| **事件总线** | Redis Stream（仓内 queue 已用 Redis，零新增）/ NATS（轻量，PRD 规划）/ Kafka（重，强生态） | **Redis Stream 起步**（kratos queue 运行时现成），接口按可替换设计；吞吐不足再平移 NATS/Kafka |
| **部署形态** | docker-compose（现状）/ K8s+Helm / Serverless | **compose→K8s+Helm**（P1）；多架构镜像已具备，顺路覆盖信创（飞腾/鲲鹏）。瓦片走 MinIO 对象存储 |
| **移动端** | uni-app（仓内现成）/ Taro（仓内现成）/ 原生 | **uni-app**（巡检作业 H5+微信小程序即可覆盖），Taro 保持平行存量不新增投入 |

## 3. "更好的解决方案"清单（反直觉但显著降本）

1. **不迁移就是最好的迁移**：约 25% 功能建议直接废弃而非重写——Jeecg/RuoYi 系统管理、三处重复 WebSocket、双套 DMA 复制代码、old_vue_gis2.0、在线表单（评估后大概率弃）。被 10 号矩阵标记"废弃/复用"的 30+ 项不需要任何开发。
2. **代码生成器是重构杠杆不是玩具**：cnd（24 表）、asset 域是纯 CRUD 域，用仓内 code_gen 起步可把人周级工作压到天级；先补齐其 PG 迁移脚本生成（仓内已支持 postgres 目录）。
3. **坐标清洗前置为独立交付物**：JSON 坐标→geometry 的 ETL 不是迁移的附属步骤，而是**第一交付物**——没有干净的空间数据，五类分析重写无从对拍。ETL 用 Python+GDAL 一次成型，失败行进隔离表。
4. **MCP 工具先行于前端**：分析域重写后先注册 MCP 工具（自动生成），前端界面后置——重构期间可用 AI 会话直接验证算法正确性，也提前产出演示价值。
5. **黄金用例对拍代替全量回归**：五类分析/DMA 从 1.0/2.0 抽取输入输出对（黄金用例 JSON），Go 重写后逐对 diff；比"重新测试整个系统"便宜一个数量级。
6. **一套登录贯通四端，RBAC 自建但复用"设计"**：portal/uni-app/管理后台/大屏共用同一 JWT 签发域与登录页体系；用户/角色/菜单/权限全新自建（ADR-12 D4），但认证中间件、令牌刷新、菜单授权粒度设计**借鉴 kratos-admin 已验证的实现**，只换数据模型不重造轮子；数据字典各子系统独立（D5），表结构用同一模板生成。
7. **把"介质分型"做进数据模型而非菜单**：用租户级配置 + 字典项（燃气/水务/热力）驱动，避免 GIS1.0 use_type 菜单分叉式的三份维护。

## 4. 决策建议（一页版）

1. **主线定 C**（骨架 pg18-unified + 事件驱动数据面 + MCP 先行）；A 留作停机约束下的 fallback；D 已确认为演进路线（D8）。
2. 六个分叉点的默认选型即第 2 节建议列，已写入 12-技术决策记录ADR.md。
3. P0 顺序：**坐标 ETL → 管网域落地（pipe/equipment/collect/alarm）→ 五类分析 Go 重写（黄金用例）→ MCP 工具注册**。
4. 验收权威=04 号 F- 清单 + 02 号里程碑：✅/⚙️→✅、重写项→对拍通过、废弃项→出冻结清单。
