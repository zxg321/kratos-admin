## D1 前端框架：Vue3（维持）

- **决策**：新 GIS 体系前端统一 Vue3（与 GIS2.0 一致），pnpm + turbo monorepo 组织。
- **影响**：GIS2.0 的 Vue3 页面结构、组件划分经验可直接参照；GIS1.0 Vue2 代码仅作业务逻辑参考。

## D2 地图引擎：锁定 AMap，MapLibre 方案全部剔除（2026-09-14 强化）

- **决策**：新系统唯一地图引擎为 **高德 AMap JSAPI**（同 GIS1.0/GIS2.0），**不迁移 MapLibre**；"向 MapLibre 迁移"类方向判定为不合理，全部剔除。现状核实：`gis/portal` **已完成 MapLibre→AMap 迁移**（20260909 迁移设计已实施落地：`AMapAdapter` + 引擎无关 `MapAdapter`），剩余工作仅为清理 maplibre-gl 残留依赖与落实缩放级清晰度指标。
- **硬性指标（新增）**：地图在 **18、19、20 缩放级及以下必须清晰**——
  1. 自有要素（管网/设备/标注）以 AMap 矢量覆盖物绘制，天然矢量渲染，各级清晰；
  2. 底图须确认图源在 18-20 级可辨（AMap JSAPI 最大 20 级：街道/建筑物级）；影像底图选源时以 18-20 级清晰度为验收项；
  3. 自建瓦片（CAD 底图、无人机影像等）金字塔必须覆盖至 20 级，缺级不得出现空白/模糊；
  4. 高缩放级性能验收：20 级下要素绘制/交互不掉帧（矢量要素按视野范围分级加载）。
- **背景**：GIS2.0 的 GISMap 包（MapContainer、绘制插件 PolygonDrawer/LineDrawer/RectDrawer/AreaSurvey、MarkerSetter、Adsorb 吸附）是成熟资产；MapLibre 迁移已判定为不合理方向，不再作为任何备选。
- **影响与注意点**：
  1. `gis/portal` 已在 AMap 上运行：清理 apps/portal 依赖表 maplibre-gl 残留；bbox 查询/分析工具栏/坐标系约定的业务逻辑平移保留；GIS2.0 的 GISMap 包（绘制/量算/吸附插件）作为新前端共享包直接演进；
  2. **授权合规**：AMap JSAPI 需要商用 key 与配额管理，key 不得入库（环境变量/配置中心管理）；
  3. **坐标系**：维持既有约定——**库内统一 WGS84(4326)，展示层 GCJ-02**，入库即转换（gcoord），不因引擎选型改变；
  4. GISMap 包作为新前端 `packages/` 下的共享包直接演进（Vue3 版本）。

## D3 三维：暂不引入 CesiumJS

- **决策**：当前无 3D 孪生订单，不引入 CesiumJS/3D Tiles/3DGS。
- **预留**：若后续签订 3D 数字孪生订单，再评估 CesiumJS（届时 2026 生态 MVT→3D Tiles 已打通）或 AMap Loca 3D 路线；管线数据模型（gis_pipe 等）保持三维可扩展（预留 z 值/高程字段）即可。

## D4 一套登录贯通四端（维持；大屏端并入，见 snop-实施规划/04 F-S02），但 RBAC 全新自建

- **决策**：portal（GIS 工作台）、管理后台、移动端 uni-app 共用同一套登录/JWT；**但用户/角色/菜单/权限体系全新设计自建，不复用 kratos-admin 的 admin 系统（base_user/base_role/base_menu/Casbin 管理界面等）**。
- **落点**：新建独立 `auth`/`acl` 业务域（建议与 GIS 同库或独立 system 库，proto 契约进 `backend/api/proto` 或 gis proto 体系）：
  - 登录签发：JWT（access/refresh）——**实现可借鉴 kratos-admin 的认证中间件与令牌机制**（kratos-kit authn），但用户/角色/菜单数据模型自建，不继承 base_* 表。
  - 权限模型：用户→角色→菜单/按钮/API 权限，按 GIS 业务重新梳理角色矩阵（总后台管理员、企业(EP)管理员、GIS 作业员、巡检员、IoT 运维、大屏访客等），替代 GIS2.0 的 admin/ep 双后台 + 海云汇外部权限。
  - 三端贯通方式：同一 token 签发域 + 按 client_type（PC/APP/大屏，沿用 GIS1.0 sys_permission 的成熟维度）区分菜单与路由授权。
- **影响**：09/10/11 文档中"base_* 直接复用 ★★★★★"的结论**降级为"可选复用（文件/消息/审计等无账号耦合的能力）"**；RBAC 相关 21 项底座复用清单中的用户/角色/菜单/字典/租户/登录策略 6 项改为自建。

## D5 数据字典：各子系统相互独立（推翻原"收敛公共字典"建议）

- **决策**：**不收敛**到统一 base_dict；每个子系统（gis（含 dma，dma 归 snop_gis 域，无独立子系统/库）/ patrol / iot / cnd / asset 等）维护**独立字典表**（如 `gis_dict/gis_dict_item`、`patrol_dict/...`），独立增删改查与缓存。
- **背景**：GIS2.0 时代字典曾在 7 库重复维护被视为债；但业务方需要各子系统字典互不干扰、独立演进（介质分型燃气/水务/排污的字典差异大），集中式字典反而增加耦合。
- **实现建议**：字典表结构与读写服务**用同一套模板生成**（结构一致、数据独立、可统一管理界面按子系统切换），既满足独立性又不放弃维护效率；跨子系统确实共用的少量枚举（如坐标类型、状态通用码）各子系统各自维护副本，不做外键级联。

## D6 数据库：每个子系统独立一个库（2026-09-14 新增）

- **决策**：**每个子系统独立一个 PostgreSQL database**，不共用单库多 schema。默认库清单（可按实施微调）：

| 库 | 承载域 | 空间/时序扩展 |
|---|---|---|
| `snop_system` | auth/acl（用户/角色/菜单/权限）、平台配置、跨域少量公共数据 | 无 |
| `snop_gis` | GIS 核心：图层/要素/管网域（pipe/equipment/collect/alarm）+ DMA 分析 | **PostGIS 4326** |
| `snop_patrol` | 巡检闭环：计划/工单/轨迹/隐患/取证 | PostGIS（轨迹/区域） |
| `snop_iot` | IoT：设备档案/驱动/事件/告警 + 时序数据 | TimescaleDB（或外接 TDengine） |
| `snop_cnd` | 指挥调度：事故/预案/物资/值班 | 无 |
| `snop_asset` | EAM 资产：台账/维保/采购 | 无 |

> 库名按平台代号 SNOP 前缀（D7）；表前缀仍按子模块（`gis_`、`patrol_`…），库与表前缀解耦。

- **机制支撑（现成）**：kratos-admin 配置体系原生支持多数据源——`data.databases` 命名数据源（`backend/configs/data.yaml`），迁移目录规则 `migration/assets/v0.0.1/<database-type>/<data-source>/` 支持按命名数据源组织各库独立初始化 SQL（详见 05 号文档 §3.1）。GORM 客户端按数据源注入各域 biz/data 层。
- **跨库纪律**：
  1. **禁止跨库 JOIN**：跨域引用（如巡检记录引用 GIS 要素、告警引用设备档案）只存 ID + 必要冗余快照字段，取详情走域间 gRPC 契约；
  2. 字典独立（D5）与独立库天然一致：各库各自 `*_dict/_dict_item`；
  3. 跨库统计（大屏/报表）由各域提供聚合接口，上层服务聚合；不建跨库视图；
  4. 部署默认同实例分库（运维面单一），高负载子系统（gis/iot）可平移独立实例，连接串仅改配置；
  5. 每库独立备份策略（kratos-admin 备份任务按数据源记录，天然支持）。
- **与既有结论的关系**：推翻"统一 schema/单库收敛"倾向（09 文档原"数据层统一规划"按库收敛的表述按本条修正）；与 GIS2.0 的 7 库模式形似，但本质不同——旧 7 库是 MySQL 无序分库+字典重复，新分库是**按域边界的有意隔离 + 契约化跨域访问**。

## D7 平台命名与定位：智慧能源运营管理一体化平台 SNOP，GIS 为子模块（2026-09-14 新增）

- **决策**：重构目标平台正式定名——**智慧能源运营管理一体化平台，代号 SNOP**；**GIS 为其子模块**，与巡检（patrol）、IoT、指挥调度（cnd）、资产（asset）、认证权限（auth/acl）等并列。
- **命名规则**：
  1. 库名统一 `snop_` 前缀（见 D6 库清单：snop_system / snop_gis / snop_patrol / snop_iot / snop_cnd / snop_asset）；
  2. 表前缀仍按子模块（`gis_`、`patrol_`、`iot_`…），库与表前缀解耦；
  3. Proto 包名维持按域（gis.admin.v1 等），服务/应用/前端包名可带 `snop` 标识（如 snop-gis-backend、@snop/gis-core）；
  4. 文档、仓库 README、docker-compose 服务名在实施时统一更名。
- **定位口径**："智慧能源"意味着介质分型从燃气/水务/排污扩展为**能源运营全域**（燃气/水务/热力等，电力等留扩展位）——介质分型继续走租户级配置（见 11 §3.7 建议），不新建分叉代码。
- **影响**：此前文档以"GIS 重构"为主线叙述，现明确为 **SNOP 平台重建、GIS 为首批子模块**；巡检/IoT/cnd/asset 等域与 GIS 平级承接，底座（auth/acl、文件、消息、审计等）为平台公共服务。

## D8 商业演进路线：方案 C 落地后向方案 D（SaaS 产品化）演进（2026-09-14 新增）

- **决策**：确认 **方案 D（SaaS 产品化）为后续商业演进方向**——方案 C（统一底座 + 事件驱动 + MCP 先行）完成 M1-M4 后，平台向"多租户 SaaS + 私有化部署双轨"产品化演进；详细方案见 `snop-实施规划/03-SaaS产品化演进方案.md`。
- **对 C 阶段的约束（SaaS-ready 预留，不增加当前工作量）**：
  1. 租户体系从第一天就按"租户=订阅主体"设计（D4 已定，无需返工）；
  2. 介质分型/功能可见性一律走租户级配置驱动（D5/D7 已定），禁止编译期分叉；
  3. 模块边界保持 proto/module 清晰（拆包售卖的最小单元）；
  4. 计量埋点（点位数/用户数/调用量）在 P1 域接口层预留字段与事件，不做计费逻辑。
- **影响**：09/11 文档中"方案 D 为远期选项"升级为"已确认演进路线"（本次修订已落实 09 §4、11 §1/§4 的 D8 标注）；里程碑在 M4 后增加 P-D1~P-D4 产品化阶段（编号 P- 前缀以区别决策编号 D-）。
