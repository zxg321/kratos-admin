## 4. 业务域落地方案（核心）

### 4.1 系统管理与认证 ——【已达容量，直接复用】
- provision 现有 `base_*`：用户/角色/菜单/部门/岗位/字典/租户/应用/登录策略/操作日志/文件，即可覆盖 gis2.0 admin 的"系统管理 + RBAC + 企业(EP)后台账号体系"。
- 企业管理后台映射：租户=企业（EP），超管 super=平台总后台。`GisSet 企业初始化参数` ↔ `base_tenant` + `base_config`；`GisDict/GisDictItem` ↔ `base_dict/base_dict_item`（三个库重复字典收敛到一处）；`GisIconDeviceLibrary/GisIconProject/GisNominalDiameter` ↔ 新增 `gis_device_config` 域。
- **微小新增**：`gis_device_type`（设备类型）、`gis_layer_setting`（图层设置）前端管理页。

### 4.2 管网 GIS（java_gis2 域）——【部分已具备，重点扩展】
落点：`gis/backend`（独立 PostGIS 库，表前缀 `gis_`）。
- 已具备：`layer` / `feature` / `analysis`（测距/测积/缓冲区/叠加）。
- 需新增 Proto 契约与实现（`gis/admin/v1` 扩展或新文件）：
  - `pipe`：管网（节点-边）数据模型 —— `gis_pipe`、`gis_pipe_point`、`gis_pipe_net_part`、`gis_pipe_valve`、`gis_landmark`。
  - `equipment`：设备/仪表/设施 —— `gis_acquisition_terminal`、`gis_detection/flow/pressure/monitor_meter`、`gis_monitor_control`、`gis_facility`、`gis_fire_fighting_equipment`、`gis_transmission_distribution_equipment`。
  - `collect`：采集数据导入与变动追踪 —— `gis_collect_data(+point)`。
  - `alarm`：告警配置与告警信息 —— `gis_alarm_config/info`。
  - `analysis` 扩展：将 legacy 图遍历类分析（关阀影响范围、拓扑、连通性、开挖、图形分析）移植到 `internal/biz` 的 `internal/analysis` 纯内存算法包（Node-Edge 图模型 + DI 注册聚合，参考旧报告 P0）。坐标统一 SRID 4326，前端 GCJ02。

### 4.3 巡检（java_patrol2.0 域）——【新业务域，独立模块】
新增 `patrol` 服务（可并入 gis/backend 或独立 `patrol` Go 模块，前缀表 `gis_patrol_`）：
- 巡检对象：`gis_patrol_pipe/…Meter/valve`、patrol_pipe_region、patrol_point。
- 工单：`gis_patrol_work_order(+task/execute)`、planning_work_order、hidden_dangers、hidden_danger_generic_plan、excavation 系列、online_upload、staff_track、device_meter_reading、video_evidence。
- 接口：`/patrol/overlay`（标定/巡查/审核）、`/work/order`、`/planning`、`/tracking`、`/disposalWork`、`/statistics`、`/background`、`/dict`。
- 轨迹与轨迹展示依赖 GIS 底图，复用 `.4.2` 的 layer/feature。

### 4.4 IoT（java_iot_dev + java_gis2.0_iot）——【新业务域，独立模块】
新增 `iot` 服务：
- MQTT 设备接入（Go：Eclipse Paho）+ 消息解析适配链；设备档案/驱动（`ep_dev_drive`）。
- 时序数据：TDengine（legacy 已用，可保留，REST 驱动）或退化为 PG 分区表；`device_data`、`…meter_data`。
- WebSocket 实时推送（告警/设备数据）→ 复用 base notification + ws。
- 接口：设备最新数据、实时用量、历史曲线。
- 与 GIS 打点联动：前端 `useDeviceMarker` 结合 `feature` + `iot` 数据渲染业务点。

### 4.5 指挥调度/应急（maida_cnd + doc/指挥调度）——【新业务域】
新增 `cnd` 服务（表前缀 `cnd_`）：
- 事故接报（accident）→ 抢险工单（rescue_work_order+execute）→ 报告提交/审核 → 演练 → 值班管理（duty）→ 应急预案（emergency_plan）→ 应急组织/协调单位/防护目标 → 物资仓库（storehouse/material/收发退）→ 监控设备 → 基础配置。
- 完成度参考 doc/指挥调度 HTML 原型：接警→启动→资源配置→现场指挥→救援→恢复→总结全流程。
- 物资/人员/车辆/值班等为普通 CRUD 域，是高端 kratos-admin 新增业务模块的最佳样板，可大量复用 code_gen。

### 4.6 设备档案与工单对接（doc 需求）——【增量】
- 设备档案系统（调拨/改装改造/报废/变卖）→ 挂在 `equipment` 或 `asset` 域，加档案状态流转。
- 工单对接 BPM → 封装 `workorder-gateway` 适配器，对接外部 BPM HTTP/OpenAPI（创建/审批/回退/转办/取消/待办/批量查询），业务侧提供状态回写接口。

### 4.7 公共消息/帮助/推送（java_gis_public）——【复用 + 小扩展】
- GIS 消息/帮助/用户 → 复用 `base_message`、`base_i18n`；公共日志 → 复用 `base_operation_log`。

## 5. 数据层统一规划

- 单一 PG 实例内分 schema 或分库：`gis`（管网/设备/图层/要素）、`patrol`（巡检）、`iot`（实时+时序）、`cnd`（指挥调度）、`system`（复用 `kratos_admin` 库既有 base_*）。
- 迁移脚本统一 `migration/assets/*/<version>/postgres/`，按域组织，字段全中文注释；GIS/巡检空间表启用 PostGIS（SRID 4326），加 `gis_` 前缀（GIS 主域）/ `gis_patrol_`（巡检）。
- legacy 7 库中 `maida_iot`（2 表）、`maida_push_data`（2 表）直接收敛进 `iot`/管道域；字典表多库重复 → 收敛到 system 公共字典。
- 建议做一份 legacy→target 的**表映射清单**（原表 → 目标表/保留/归档/废弃），作为迁移 SLA 依据，含 `_history` 历史表保留策略。

## 6. 前端体系规划

- 管理后台（对接 base_* + 各业务域）：基于 `frontend/admin` monorepo 新增页面 —— 系统管理（复用现有）、设备类型/图层设置/口径/图标库（`.1`）、巡检工单/轨迹、指挥调度、档案等。
- GIS 工作台：扩展 `gis/portal`（MapLibre GL）—— 多底图源 LayerRegistry（天地图/高德影像 WMTS/XYZ）、设备打点渲染器 `useDeviceMarker`、吸附/绘制/量算（继承旧报告 P1）、接入管线/阀门/仪表图层、大屏视图（ECharts）。
- uni-app / taro-app：巡检移动端（轨迹上报、隐患取证、工单执行）可落在 `frontend/uni-app`。
- 明确**不迁移**：micro-app 微前端（与 monorepo/RBAC 重叠）、AMap 引擎（坐标系偏移 + 与 MapLibre 冲突）。

## 7. 接口契约与生成流程

遵循仓库 AGENTS.md（契约 → 后端 → 前端 → SQL/文档 同改）：
1. 新增业务域的 proto 放 `backend/api/proto/<domain>`（admin/app）× 对应模块；GIS 扩展放 `gis/backend/api/proto/gis/admin/v1`。
2. `make api` / `make gen` 生成 `api/gen`、`rpc`、OpenAPI（宿主机制造链，勿在精简镜像容器内跑生成）。
3. GORM 模型由动态表源/gorm-gen 生成，但本分支为 PG，统一用生成的 PG 模型。
4. 前端经 `frontend/admin` 的 API 封装 + portal 的 `api/` 对接。

| GIS/算法价值 | **8.0** | 图遍历算法与空间建模有稀缺价值；叠加查询/多图层已具备 |
| 迁移工作量 | **6.5** | 7 业务域、150+ 表、3 套前端，工作量大；IoT/时序/指挥调度为全新域 |
| 数据/坐标风险 | **7.0** | MySQL→PG、GCJ02 数据清洗、多库表归并是最大重构成本 |
| 整体综合 | **7.5** | 可实现且价值高，但必须按域分期 + 表映射清单控制范围 |

### 9.2 潜在问题与合理化建议

1. **范围爆炸（最主要风险）**：7 个业务域全做会超出周期。→ 严格按 P0→P1→P2，每域先出"表映射清单 + 契约"，验收后进入下一域。
2. **MySQL→PG 方言与空间差异**：gis2.0 全为 MySQL + 坐标系混乱（高德 GCJ02）。→ 本分支一律 PG+PostGIS(SRID 4326)；接入层统一 GCJ→WGS84 转换；禁止新增 MySQL 分支代码。
3. **坐标漂移**：高德图元/前端坐标 GCJ 与库内 WGS 叠加偏移。→ 统一入库即转 WGS84，前端才转 GCJ02（沿用现有约定），文档固化。
4. **多库字典/设备表重复**：dict、设备表在 maida 多库并存，历史表庞大。→ 收敛公共字典到 system；设备主数据去重（原 tools/重复筛选.sql 思路）后在目标库唯一建模；`_history` 定保留策略。
5. **IoT/TDengine 与 MQTT**：Go 需重新实现 legacy 的适配链与 MQTT 解析。→ 设备消息 schema 先行；时序库 TDengine 可保留（REST 驱动）或退化为 PG 分区；与告警/打点解耦。
6. **外部 BPM 对接**：工单对接强依赖外部流程平台。→ 以适配器 + 幂等 + 超时重试承接，接口契约先行并与其协商字段。
7. **前端引擎选型迁移**：AMap→MapLibre 使绘制/吸附/量算插件无法直接复用。→ 只抽象"图层源 + 业务点渲染器"，引擎绑定收敛在 gis-core，避免两层漂移。
8. **认证与租户语义对齐**：legacy 网关 JWT 与本项目 JWT+租户体系需对齐。→ 全量走本项目认证中间件；租户=企业(EP)映射，非超管强制隔离（沿用 `resolveTenantScope`）。

### 9.3 结论
kratos-admin 技术栈**足够完整支撑 gis2.0 的绝大部分能力落地**，且通用后台可直接复用，价值集中在管网 GIS 扩展与巡检/IoT 新域。建议以 **P0 管网扩展 → P1 巡检+IoT → P2 指挥调度+档案/BPM对接** 分域推进，每域以"表映射清单 + proto 契约"为交付门禁，将 7 库/150 表/3 前端拆成可控增量。
