### 1.3 存量瓶颈（本次重建的动因）

1. **双前端体系并存、强重复**：`old_vue_gis2.0` 与 `vue3_gis2.0` monorepo 结构/包几乎一致；`admin` 是另一套 pure-admin-thin 模板 → 三套前端生态维护成本高。
2. **模块耦合、边界弱化**：`gis-infrastructure` 直接依赖 `iot-data-api / gis-patrol-api / gis-api-ep`；DDD 分层名存而边界模糊；orm/Swagger/JUnit 版本混杂（mybatis-plus 3.3 与 3.5 并存、springfox 2.9 与 springdoc 2.6 并存、junit 3.8.1）。
3. **无统一消息总线**：依赖 MQTT + 定时任务 + Feign 同步推送，跨服务事件（设备数据→GIS→告警→工单）链路脆弱、易丢。
4. **地图强锁高德（GCJ02）**：坐标系为 GCJ02 展示，缺底图切换与标准 WGS84/数据中台衔接；几何库强耦合前端。
5. **空间分析能力弱**：关阀/开挖/连通/拓扑分析依赖应用层计算，无数据库空间索引支撑，大范围分析性能受限。
6. **时序与关系分库**：TDengine + MySQL 双库，数据一致性与运维复杂；`dynamic-datasource` 多库路由增加心智负担。

## 二、2026 目标技术栈（承接本项目 + 业界最新）

### 2.1 后端（继承 Kratos v3 已定基线）

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | **Kratos v3**（go-kratos/kratos/v3） | 已定为项目基线，gRPC + HTTP 自适应，Wire 依赖注入 |
| 空间库 | **PostgreSQL + PostGIS 3.x** + GiST 空间索引 | 全量空间分析与查询下沉数据库，WGS84(4326) 存储计算 |
| 时序 | **TimescaleDB（PG 扩展）**（推荐）或保留 TDengine | 若坚持 PG 单库统一，用 Timescale 原生时序超表，消解双库 |
| 中间件 | **NATS / Kafka**（跨服务事件总线） | 设备上行→GIS→告警→工单解耦；MQTT 保留为设备协议层 |
| 鉴权 | JWT + RBAC + 租户隔离（Webhook/中间件） | 沿用项目既有 resolveTenantScope 语义 |
| 可观测 | Prometheus + OpenTelemetry + slog | 指标/Trace/日志统一 |
| 存储 | Redis（缓存/会话/最新状态）、MinIO（图片/标定/视频证据） | 沿用 |
| AI | Go + 外调模型服务（图像识别/时序预测） | 见 §4 |

### 2.2 前端（承接 Vue3 栈 + 2026 最新）

| 层 | 2026 最新选型 | 说明 |
|---|---|---|
| 框架/构建 | **Vue 3.5+ / Vite 7 / TS 5.8**（按需升级） | pnpm monorepo + Turborepo 收敛，统一三套前端为 **一套** |
| UI | **Element Plus** 或 **Arco Design Vue** | 顶栏/侧栏一体化 Admin Shell |
| 状态 | Pinia（规范化，废弃自定义 global-store 混用） | 统一 store 边界 |
| 图表 | **ECharts 6** | 密集点位用 canvas 优化 |
| 地图 | **MapLibre GL（开源标准，首选）+ 高德适配层** | 底图可切换（天地图/OSM/高德标记），几何前端展示统一 WGS84↔GCJ02 由 `gcoord` 收敛（避免混用） |
| 样式 | Tailwind CSS + SCSS 设计令牌 | dark/light 双主题 |
| 大屏 | DataV 组件 / three.js(数字孪生) | BIM 对接（`push_zy_pipe_bim`） |

### 2.3 架构姿态

```
[一协作式一体前端 Admin Shell]
        │ REST/gRPC
        ▼
[API 网关 Kratos Gateway]
        │
   ┌────┴────┐
   │ BFF/聚合层│
   └────┬────┘
┌───────┼──────────┐
[管网域][采集域][监测域][巡检域][指挥域][设备资产域][系统域]
   │  ├  PostGIS(空间)      ├  TimescaleDB(时序)
   │  └  NATS事件总线 ←── MQTT 设备上行链路
   └────────────┐
  [AI 能力层：识别/预测/智能派单/RAG预案问答]
```
- **单域一服务（bounded context）**，跨域仅通过事件总线与 API 契约交互，杜绝 `infrastructure` 跨模块直接依赖。
- **数据中台**：PostGIS 统一空间资产，GIS 前端展现层薄化，空间计算全部下沉。

## 三、产品规划（升级后的「一体化」定位）

> 产品定位转变：从「GIS 数据展示 + 多系统拼盘」→ **以管网资产为核心、监测-巡检-应急-资产全链路闭环的智能运维一体化平台**。
> 价值主张：一张图看到底（态势）、一条链管到底（事件）、一套数用到底（资产）。

### 3.1 信息架构（8 大模块）

| 模块 | 关键页面 | 升级亮点 |
|---|---|---|
| **态势总览（一张图）** | 首页大屏：管网态势 / 监测实时 / 告警热力 / 巡检在线 / 应急状态 | 多源实时数据拉通，一屏掌握全网 |
| **管网一张图** | 图层树 / 管网编辑 / 关阀影响 / 开挖分析 / 连通与拓扑分析 / 埋深断面 | 空间分析全下沉 PostGIS；关阀影响智能联想 |
| **智能监测告警** | 设备总览 / 实时数据 / 阈值配置 / 告警中心 / AI 预测预警 | 预测性维护、批量阈值、告警聚合降噪 |
| **采集作业与成果** | 采集批次 / 点位明细 / RTK/CAD 导入 / 质检入库 | 采集→校验→入库→一张图闭环 |
| **巡检作业** | 计划工单 / 巡检执行 / 轨迹回放 / 隐患上报 / AI图像识别 / 损益对标定 | 移动作业 + AI 缺陷识别 |
| **应急指挥调度** | 事故接报→派单→处置→物资→报告；值班排班 / 预案 / 演练 | BPM 审批 + 事件闭环 + 数字预案 |
| **设备资产全生命周期** | 资产台账 / 调拨 / 改装改造 / 标定 / 报废 / 变卖 | 全生命周期 + 档案追溯 |
| **系统与数据管理** | 类型/字典/口径/图标/角色/租户/日志 | 租户数据隔离、审计 |

### 3.2 关键闭环设计

1. **「设备数据→告警→处置」闭环**：MQTT 上行 → NATS 事件 → 监测域规则引擎告警 → 巡检/应急域按等级派单 → 处置回写 → 归档。
2. **「采集→质检→入库→纳管」闭环**：RTK/CAD 导入后空间校验（拓扑、重合、悬挂点）→ 生成入库任务 → PostGIS 写入 → 关联设备资产。
3. **「隐患/异常→虚→实」闭环**：AI 图像识别隐患图片生成巡检工单 → 现场确认 → 隐患登记 → 挖掘/施工联动监控。
4. **「体系建设→演练→实战」闭环**：预案数字化 → 演练 → 复盘报告 → 预案修订。

### 3.3 AI 智能增强（2026 竞争力）

| 能力 | 落地方式 | 价值 |
|---|---|---|
| 管线缺陷/抄表 AI 识别 | 标定与隐患图片 → 视觉模型 | 巡检效率提升、降低漏检 |
| 预测性维护 | 时序数据(压力/流量) → 异常预测 | 泄漏/过压提前预警 |

| 智能派单/路线优化 | 位置 + 工单 + 车辆 → 推荐派单 | 响应提速 |
| 预案 RAG 问答 | 预案/制度知识库 → 语义问答助手 | 一线快速参考 |
| 数字孪生 + BIM | three.js + `push_pipe_bim` 模型 | 直观决策 |

## 五、风险与建议

| 风险 | 建议 |
|---|---|
| 200+ 表一次性迁移工作量大 | 按业务域分批（P0→P4），逐域灰度；保留旧库只读比对期 |
| 时序从 TDengine→Timescale 迁移 | 先做双写试探，脚本校验；或保留 TDengine 以最小变更上线 |
| 地图由高德锁定迁移 MapLibre | 增加底图适配层，坐标统一 gcoord，先双轨再收敛 |
| 双/三前端收敛人力成本 | 以 monorepo 收敛 packages 为先，old_vue 直接归档 |
| 业务规则隐于旧代码（阈值/拓扑算法） | 建立「行为清单」，用 golden-file 对比回归测试兜底 |
| AI 模型依赖外部服务 | 沿用本项目 fallback 策略：模型待机 → 降级规则引擎 |
